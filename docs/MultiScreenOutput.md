# マルチモニター出力

作成: 2026/10/10(再作成: 2026/10/22、更新: 2026/11/10) / 作成者: 24CU0110 大川翔生
対象パス: `Assets/#Scripts/Camera/`

1 台のカメラの映像を、接続されているモニターの数だけ横に並べた 1 枚の RenderTexture に描き、モニターごとに該当部分を切り出して表示する。枚数・解像度・左右の並びは、起動時にすべて自動で検出して割り当てる(Inspector の手動設定はない)。モニターが 1 枚でも起動する。縦画面のモニターは描画モニターに換算せず、映像を割り当てない(下の「自動検出の規則」)。

## 構成

| ファイル | 種別 | 役割 | 作成 / 更新 |
|---|---|---|---|
| `MultiScreenOutput.cs` | シングルトン | モニターの検出と有効化、RenderTexture の作成、モニターごとの表示 Canvas の作成 | 09/27 / 11/10 |
| `MultiScreenSourceCamera.cs` | MonoBehaviour | シーンのカメラを、出力元として `MultiScreenOutput` に登録する | 09/27 / 09/29 |
| `MultiScreenTargetSelector.cs` | static class | 描画する横画面のモニターを決め、左右の並びから映像番号を求める(Unity に依存しない判定) | 11/10 / 11/10 |
| `WindowsMonitorInfo.cs` | static class | Windows API で、モニターの枚数・配置・メイン判定・解像度・縦画面判定を取得する | 09/27 / 11/10 |

## 仕組み

```
  カメラ(1 台)── 描画 ──▶ RenderTexture(幅 = 1 台分 × 枚数、高さ = 1 台分)
                                      │  モニターごとに、横方向の範囲を切り出す(uvRect)
                 ┌────────────────────┼────────────────────┐
             Display[1]           Display[0]           Display[2]
             (左から 1 番目)       (メイン、2 番目)       (左から 3 番目)
```

- 上の割り当ては、3 画面の実機での出力例。
- 映像は 1 回だけ描き、モニターごとに切り出す。モニターごとにカメラを置く方式ではない。
- 切り出した範囲は、そのモニターの画面いっぱいに引き伸ばす(解像度の違うモニターは伸びる)。
- 表示は `ScreenSpaceOverlay` の Canvas を、モニターごとに 1 枚(`targetDisplay` にディスプレイ番号)。

## 起動の流れ

| 順 | 処理 | 内容 |
|---|---|---|
| 1 | `Awake()` | 重複なら何もしない。Windows API と Unity のモニター一覧をログに出す(Editor と Development Build のみ) |
| 2 | Editor | 出力枚数を 1 にして終える(通常の Game View を維持) |
| 3 | `DetectDisplays()` | Unity のディスプレイと Windows API のモニターから、それぞれ縦画面を除いた横画面を集め、先頭から順に対応させて(仮の対応)描画モニターと枚数を決める → メインの解像度を決め、全画面ウィンドウで設定。ディスプレイの有効化はここでは行わない |
| 4 | `Start()` | RenderTexture を作る。登録済みのカメラがあれば出力先を設定。コルーチン(`SetupDisplayCanvasesRoutine`)を始める |
| 5 | `ActivateDisplaysRoutine()` | メイン以外の描画モニターを **1 枚ずつ**有効化し、そのたびに現れた Unity のウィンドウがどのモニターにあるかを Windows API で調べて、仮の対応を実際の配置に置き換える(下の「自動検出の規則」)。確認できなければ仮の対応のまま警告。そのあと映像の割り当て(左右)を決める |
| 6 | Canvas の作成 | モニターの有効化直後は描画が不安定なので、5 フレーム待ってから、描画モニターごとに作る(縦画面には作らない) |
| 7 | `OnDestroy()` | カメラの出力先を外し、RenderTexture を解放する |

- `SetSourceCamera(_camera)` で出力元のカメラを切り替える。RenderTexture が作成済みなら、直ちに出力先を更新する。
- 実機では、カメラの `targetTexture` を RenderTexture にし、アスペクト比を RenderTexture の幅 ÷ 高さに合わせる。出力元が未登録なら、エラーログを出して何もしない。
- Editor では分割しない。`targetTexture` を外して Display 0 に直接描き、表示 Canvas も作らない(Editor で RenderTexture に描くと「No cameras rendering」の表示や白い画面になるため)。分割した出力の確認は、ビルドで行う。

## 自動検出の規則

| 項目 | 規則 |
|---|---|
| 出力枚数 | 横画面のモニター数(描画モニター数)。Windows API の横画面と Unity の横画面を比べて、少ない方。下限 1。食い違うと警告を出す。Windows API で取れなければ、Unity が縦画面と報告したものを除いた Unity の台数 |
| 縦画面 | 高さが幅より大きいモニター。Windows API 側は物理解像度(`WindowsMonitor.IsPortrait`)、Unity 側は `Display.systemWidth` / `systemHeight` で判定する(回転による縦向きも、もともと縦長のパネルも含む。正方形は縦画面にしない)。**描画モニターに換算しない**: 出力枚数・RenderTexture の幅・左右の並びの数に入れない / `Display.Activate()` しない / 映像の切り出しと表示 Canvas を割り当てない。Unity のディスプレイ番号は詰めない。除外したときは通常のログを出す。メインモニターだけは、ゲームウィンドウの表示先で除外できないので、縦画面でも描画モニターに含めて警告を出す |
| 1 枚の解像度 | メインモニターの物理解像度(Windows API)。取れなければ Unity の `systemWidth` / `systemHeight`。それも無理なら 1920×1080 |
| RenderTexture | 幅 = 1 枚の幅 × 枚数、高さ = 1 枚の高さ、深度 24 ビット |
| 左右の並び | 各描画モニターの `m_pixelRect.x`(左端の座標)が小さい順に 0, 1, 2 …。同じ座標なら Unity のディスプレイ番号が小さい方が左 |
| Unity と Windows の対応 | **番号では対応させず、実際の配置を OS に確認する。** Unity の番号と Windows API の列挙順は、PC や構成によって一致しない(2026/11/10 のテスト PC で、縦画面があると番号が起動ごとに入れ替わり、横 3 画面だけでも左右が逆になった。以前の開発用 PC では一致していた)。手順: ① 仮の対応として、それぞれ縦画面を除いた横画面を、番号順に先頭から対応させる(`MultiScreenTargetSelector`) ② メイン以外の描画モニターを 1 枚ずつ `Activate()` し、そのたびに増えた Unity のウィンドウ(クラス名が `Unity` で始まる、自分のプロセスの表示中のもの)が載っているモニターを `MonitorFromWindow` で調べる ③ モニターのデバイス名で Windows API の一覧と突き合わせ、仮の対応を置き換える。メインは、有効化の前からあるウィンドウが 1 つだけならそのモニター、それ以外は仮の対応 |
| 確認できない場合 | ウィンドウが 120 フレーム以内に現れない / モニターを特定できない / 同じモニターが重複した、のどれかなら、仮の対応(番号順)のままにして警告を出す。この場合は左右が逆になることがある |
| 取得できない場合 | モニター一覧が空なら、Unity のディスプレイ番号順をそのまま左からの並びにして警告 |
| 警告 | Unity と Windows API で解像度が異なる場合 |
| 1 枚の接続 | 異常ではなく通常の動作として、通常のログ(警告にしない) |

起動ログの例(3 画面の実機):

```
[WindowsMonitorInfo] Windowsが認識しているモニター数: 3
[WindowsMonitorInfo] Monitor[0] \\.\DISPLAY1 primary:False pixel:1920x1080@(-1920,0)
[WindowsMonitorInfo] Monitor[1] \\.\DISPLAY2 primary:True  pixel:1920x1080@(0,0)
[WindowsMonitorInfo] Monitor[2] \\.\DISPLAY3 primary:False pixel:1920x1080@(1920,0)
[MultiScreenOutput] メインディスプレイの解像度: 1920x1080 (Unityの認識: 1920x1080)
[MultiScreenOutput] Display[0] = \\.\DISPLAY2 → 左から2番目 (1920x1080@0)
[MultiScreenOutput] Display[1] = \\.\DISPLAY1 → 左から1番目 (1920x1080@-1920)
[MultiScreenOutput] Display[2] = \\.\DISPLAY3 → 左から3番目 (1920x1080@1920)
```

上は 2026/09/29 の 3 画面の実機のログ。2026/11/10 以降の `Monitor[n]` の行には、`primary:` の次に `portrait:`(縦画面か)も出る。縦画面を除外したときは、`Unityの Display[n] は縦画面(幅x高さ)のため、描画モニターに含めません。` と `Windows APIの <デバイス名> は縦画面(幅x高さ)のため、描画モニターに含めません。` が出る(リリースビルドの `Player.log` には出ない。警告だけが残る)。

## WindowsMonitorInfo

`user32.dll` を呼び出してモニター情報を取る。Windows 以外では空の結果を返す。

| メンバー | 内容 |
|---|---|
| `WindowsMonitor`(構造体) | デバイス名、メインか、`m_desktopRect`(仮想デスクトップ上の矩形)、`m_pixelRect`(物理ピクセルの現在の解像度と位置)、`IsPortrait`(縦画面か。`m_pixelRect` の高さ > 幅) |
| `GetMonitors()` | OS の列挙順で取得。失敗しても例外を投げず、空のリスト |
| `GetMonitorsInUnityOrder()` | メインを先頭に移し、残りは列挙順。名前に反して、残りの並びは Unity の `Display.displays` と一致するとは限らない(上の「Unity と Windows の対応」) |
| `GetOwnUnityWindows()` | 自分のプロセスの、表示中の Unity のウィンドウを取得する(`EnumWindows`、`GetWindowThreadProcessId`、`IsWindowVisible`、`GetClassName`)。クラス名が `Unity` で始まるものだけ。失敗しても例外を投げず、空のリスト |
| `TryGetMonitorOfWindow(_window, out _monitor)` | ウィンドウが載っているモニターを取得する(`MonitorFromWindow`) |
| `LogAll()` | 結果をログに出す。Editor と Development Build 以外では呼び出しごと除去 |

| 取りたい情報 | API |
|---|---|
| 枚数 | `EnumDisplayMonitors` |
| 配置・メイン判定・デバイス名 | `GetMonitorInfoW` |
| 物理解像度と位置 | `EnumDisplaySettingsW`(`ENUM_CURRENT_SETTINGS`) |

- `m_desktopRect` は DPI の仮想化の影響を受けることがある。実際の解像度は `m_pixelRect` を使い、`EnumDisplaySettingsW` が使えなければ `m_desktopRect` で代用する。
- IL2CPP でも動くよう、列挙のコールバックに `[AOT.MonoPInvokeCallback]` を付ける。デリゲートは `static readonly` で保持し、結果のリストは使い回す(メインスレッド専用)。構造体のサイズは呼び出し前に設定する。

## MultiScreenSourceCamera

シーンの Main Camera に付ける。`OnEnable()` で `MultiScreenOutput` の生成を毎フレーム待ち、生成されたら `SetSourceCamera` で登録する。待っている間に無効化されたら、待機だけを止める。常駐の画面出力より先にカメラが有効になっても、白い画面にならないようにするため。

## 配置と設定

| 項目 | 内容 |
|---|---|
| `MultiScreenOutput` | `Manager` シーンに 1 つ |
| `MultiScreenSourceCamera` | `Load`・`Splash`・`Opening`・`Menu`・`Map`・`Result` の Main Camera。`Loading` には付いていない |
| カメラの Viewport Rect | 上の 6 シーンとも x=0, y=0, 幅=1, 高さ=1。**幅は 1.0 にする**(狭めると、その割合の範囲にしか映らない) |
| カメラの出力先 | シーンには設定せず、実行時に `MultiScreenOutput` が設定 |
| ProjectSettings | `runInBackground` ON、`fullscreenMode` FullScreenWindow、既定の画面サイズ 2560×1440 |

他のモジュール: `SingletonMonoBehaviour`・`AppLog`(`CommonFoundation.md`)。`TransitionFadeController`・`LoadingScreenController` は `Display.displays.Length` を基にモニターごとの Canvas を作る。この仕組みの有効化は `min(Windows API の台数, Unity の台数)` で決まるので、台数が食い違うときと、縦画面のモニターがあるときは、有効化されないディスプレイ向けの Canvas ができる(表示されないだけ)。

## 未対応・要確認

| 項目 | 内容 |
|---|---|
| 起動順のエラー | `MultiScreenOutput.Instance` は、インスタンスがない状態で最初に参照されるとエラーを 1 回出す。`Manager` の読み込みより先にカメラが有効になるシーンで出る(Editor と Development Build のみ)。動作に影響なし。対策案は、`Instance` を使わず存在を確認すること |
| 古いカメラの出力先 | `SetSourceCamera` は、前のカメラの `targetTexture` を外さない。遷移で新旧のシーンが同時にある間は、2 台が同じ RenderTexture に描く。画面は覆われているので見えないが、実害の有無は未確認 |
| 解像度の違うモニター | 1 枚の解像度はメインに合わせ、他は引き伸ばす。解像度やアスペクト比の違うモニターを混ぜると、映像が伸び縮みする |
| 対応規則の確認範囲 | 番号順の対応(旧規則の「`Display[1]` 以降は列挙順」)は、以前の開発用 PC の横置き 3 画面で 2 回起動して確認した。2026/11/10 のテスト PC(RTX 4070 Ti、横 3 画面)では、この規則で左右が逆になった(`実測`。Windows API の列挙順は メイン・右・左(`DISPLAY6` / `DISPLAY7` / `DISPLAY8`)で、Unity の番号は メイン・左・右 とみられる。Unity の番号の実際の並びは、このときログに取っていない)。そのため現行の版は番号の対応に頼らず、有効化したウィンドウの位置で確かめる(上の「Unity と Windows の対応」)。**この確認方法は、Unity のプレイヤーで未実行。** Windows API の呼び出し部分は、起動中の Unity Editor のウィンドウで動くことを確認した(2026/11/10)。ウィンドウのクラス名がプレイヤーで `Unity` で始まるか(Editor は `UnityContainerWndClass`)、有効化から何フレームでウィンドウが現れるかは未確認。展示用 PC では、枚数と解像度の自動検出は確認したが、左・中央・右の並びで映ったかの記録がない。ずれた場合の代替案は、`DisplayInfo.name` と Windows のデバイス名の突き合わせ |
| 規約との差 | 定数・フィールドにアクセス修飾子がない。参照型(`Camera`、`RenderTexture`)のフィールドに `m_p` がない |
| 縦画面の除外 | 2026/11/10 に追加し、同日のテストで作り直した。最初の版は、Windows API の列挙順で「n 番目が横画面」と判定して `Display[n]` を有効化したが、実機(メイン + 横 + 縦の 3 画面)では縦画面とメインだけが描画された(`実測`。`Player.log` に `Display[2]`(1 回目)、`Display[1]`(2 回目)の「解像度が Windows API と一致しません。Unity: 1080x1920 / Windows: 1920x1080」)。縦画面の Unity の番号が起動ごとに入れ替わり、Windows API の並びと合わなかったため。現行の版は、有効化するディスプレイを縦画面を除いた横画面から選び(Unity 側は報告される解像度で判定)、左右の対応はウィンドウの位置で確かめる。有効化の対象を選ぶ判定は、実機のログと同じ並びを含む 13 件を Unity なしで実行して確認した(`コード`)。**この版での実機は未確認**。縦画面の `Display[n]` は有効化しないので、そのモニターには何も映らない(Windows のデスクトップのまま。`推定`)。メインが縦画面のときは、除外できないので描画モニターに含める(1 枚の解像度もメインの縦画面の値になり、横置きのモニターは引き伸ばされる) |
| 未検証 | モニターが 4 枚以上の場合 / 拡大縮小(DPI)の設定がある環境 / シングルモニターでの実機起動 / 縦画面のモニターがある構成の実機 / ウィンドウの位置で対応を確かめる方式の、プレイヤーでの実機 |

旧方式のスクリプト `MultiDispllays.cs`(ウィンドウ位置を固定値で指定)は、未使用のため 2026/10/10 にプロジェクト外へ退避した。

## PDCA

担当: 9 名のチーム制作のうち、画面出力の仕組み(3 本)を全面的に担当。性能の計測と HDRP の設定の見直しも担当。期間: 2026/09/27〜09/29(自動検出の実装と実機検証)、性能の比較は 2026/10/03。

用語: **5/28 版** = 2026/05/28 時点のバージョン。NVIDIA Surround(7680×1080 を 1 つのディスプレイとして出力)で、`MultiScreenOutput` はなかった。**展示用 PC** = Intel Ultra 9 / RTX 5060 Ti / メモリ 64 GB。

| | 内容 |
|---|---|
| 目標 | 会場の構成に左右されず、設定なしで画面出力が立ち上がる。3 画面の出力解像度を上げても、Volumetric Fog を保ったまま滑らかに動かす。① 1 枚でも N 枚でも起動 ② 枚数・解像度・並びを自動で検出 ③ 検出に失敗しても止まらない ④ 映像は 1 回だけ描く。達成の基準の数値は未記載 |
| 課題 | 4 つの手動設定が必要だった / 2 枚以上が前提で 1 枚では起動できなかった / Windows のモニター名の番号は物理の並びともメインとも無関係で、起動のたびに入れ替わる環境だった / モニターごとにカメラを置く方式は、2026/09/29 の試験で左右のモニターが映らなかった(ログに例外なし。原因は特定できていない) / 5/28 版は 7680×1080 で 63.6 FPS・GPU 100% が限界。今作は 7680×1440 で、総ピクセル数が約 1.33 倍(8,294,400 → 11,059,200) |
| 検証・結果 | 手動設定 4 つを廃止し、1 枚から N 枚まで設定なしで起動する。3 画面の実機(1920×1080、2026/09/29)で、自動検出どおりに割り当てられ、映像が左・中央・右に正しく映った(解像度の食い違いの警告 0 件。2 回の起動で、デバイス名の番号が入れ替わる環境でも規則が成り立った)。展示用 PC(2560×1440 の 3 画面、2026/10/03)で、枚数と解像度の自動検出を確認 / 2026/11/10: 縦画面のモニターを描画モニターに換算しない処理を追加。実機のテストで、縦画面とメインだけが描画される不具合が出た(原因は上の「縦画面の除外」)。横画面どうしを先頭から順に対応させる方式に作り直したところ、縦画面がない横 3 画面で左右が逆になった(Unity の番号と Windows API の列挙順が、PC によって一致しないため)。そこで、ディスプレイを 1 枚ずつ有効化して、現れたウィンドウの位置から対応を確かめる方式にした(ビルド用の設定でのコンパイルと、Windows API の呼び出しの動作確認のみ。プレイヤーでの実機は未確認) |
| 未記録 | 展示用 PC での左・中央・右の並びの目視 / シングルモニターでの実機起動 / 縦画面のモニターをつないだ実機での確認 / 施策ごとの FPS への効果 / 展示(TGS2026)の結果 |
| 次の候補 | 並びがずれた場合にモニター名で突き合わせる方式 / パネル本来の解像度の取得(`QueryDisplayConfig` など) / `MultiScreenSourceCamera` の起動順のエラーの解消 / カメラを増やす方式で左右が映らない原因の特定 / 施策ごとの効果を切り分ける計測 / 未実施の削減候補(Async Compute、GPU オクルージョンカリング、動的解像度の単独検討、オーバードロー可視化、影のカスケード数とシャドウアトラスの見直し) |

条件: 展示用 PC、リリースビルド、垂直同期なし、撮影位置は 3 条件とも同じ。各条件 1 枚のスクリーンショット(0.5 秒平均の瞬間値)。

|---|---|---|---|
| FPS | 63.6 | 77.9 | **88.6** |
| フレーム時間 | 15.7 ms | 12.8 ms | 11.3 ms |
| Resolution | 7680x1080 | 2560x1440 | 2560x1440(render 7680x1440) |
| Displays | 1 (active 1) | 3 (**active 1**) | 3 (active 3) |
| Cameras | 2 | 3 | 1 |
